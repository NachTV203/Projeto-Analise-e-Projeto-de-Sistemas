5.	REQUISITOS
5.1.	Requisitos Funcionais
Orientações: Cada requisito funcional deve ser descrito de forma clara e objetiva, seguindo uma estrutura padronizada composta por três elementos: um identificador único (como RF01, RF02...), um título resumido que represente a ação principal que o sistema deve realizar, e uma descrição breve da funcionalidade esperada. Exemplo: RF01 – Cadastro de Cliente: o sistema deve permitir o cadastro de clientes, incluindo nome completo, CPF, endereço, telefone e e-mail.
Texto a ser preenchido pelo grupo...
5.2.	Requisitos Não Funcionais
Orientações: Os requisitos não funcionais devem ser descritos de forma objetiva, especificando as restrições e características técnicas que o sistema deve atender. Cada item deve conter um identificador único (como RNF01, RNF02...), seguido de uma descrição clara da exigência relacionada a aspectos como desempenho, segurança, usabilidade, disponibilidade, entre outros. Exemplo: RNF01 – Desempenho: o sistema deve responder às solicitações do usuário em até 2 segundos.
Texto a ser preenchido pelo grupo...
5.3.	Regras de Negócio 
Orientações: As regras de negócio representam condições específicas que regem o funcionamento do sistema e devem ser descritas de forma clara e objetiva. Elas estão diretamente ligadas aos requisitos funcionais e não funcionais, servindo como critérios de aceitação para validar se uma funcionalidade está completa e atende às necessidades do negócio.
Cada regra deve estar associada a um requisito, indicando restrições, validações ou comportamentos esperados. Por exemplo, para o requisito RF01 – Cadastro de Cliente, uma regra de negócio pode ser: “O cliente só pode ser cadastrado se informar CPF válido e não estiver previamente registrado no sistema.” Já para o requisito RNF01 – Desempenho, uma regra pode ser: “O sistema deve processar o cadastro em até 2 segundos.”
Essas regras ajudam a garantir que o sistema funcione conforme as expectativas dos usuários e respeite as normas internas da organização. Ao escrever as histórias de usuário, essas regras devem ser consideradas como critérios de aceitação, permitindo que a equipe de desenvolvimento e os stakeholders validem cada entrega com segurança e clareza.

6.1.2.	Desenho/imagem do diagrama
•	Use ferramentas adequadas (ex.: draw.io, Lucidchart, StarUML).

6.1.3.	Descrição dos Casos de Uso
Orientações: Para garantir clareza e rastreabilidade no projeto, cada caso de uso apresentado no diagrama deve ser descrito individualmente. A descrição deve seguir o modelo padrão, detalhando os elementos essenciais da interação entre o ator e o sistema. Essa etapa é fundamental para: Validar os requisitos funcionais com base em cenários reais; facilitar o entendimento por parte da equipe técnica e dos stakeholders; Servir como base para testes, critérios de aceitação e refinamento das histórias de usuário.
Dicas:
•	Seja objetivo e claro: Evite termos ambíguos ou genéricos.
•	Use linguagem funcional: Foque no que o sistema faz, não em como ele faz.
•	Relacione com os requisitos: Cada caso de uso deve estar vinculado a pelo menos um requisito funcional.
•	Inclua regras de negócio relevantes: Especialmente nas pré-condições e fluxos alternativos.
Modelo:
Caso de Uso:	Nome do caso de uso
Ator(es):	Quem interage com o sistema
Descrição:	Resumo da funcionalidade
Pré-condição:	O que deve estar verdadeiro antes da execução
Fluxo Principal:	Passo a passo da interação padrão
Fluxo Alternativo:	Exceções ou variações do fluxo principal
Pós-condições:	Resultado esperado após a execução
